# Multi-user accounts and sharing: cryptographic architecture (v1.2 design)

Status: design and implementation notes for `feature/v1.2-secure-sharing`. Account separation (sections 2 to 6, 9) and entry sharing (section 7) are implemented. This document and the code have had a self-review and one separate-context AI review (see SECURITY-REVIEW.md section 14). They have not had an independent human cryptographic review.

## 0. Current architecture (what is actually built)

- Pastry runs **server-side decryption**. The server process holds an account's vault key in memory while that account's session is open. A server operator, or code running as the server, can read any open vault. This is not end-to-end encryption, and the design does not claim otherwise.
- Each account's vault is protected by its master password. Argon2id derives a key-encryption key (KEK). The KEK wraps a random 256-bit **account vault key** (DEK) with AES-256-GCM.
- Every entry's metadata and content are sealed with that account's DEK, or, for entries with a separate password, with a key derived from that password. Authenticated data binds each blob to its entry's random ID and its layer.
- Sessions are in memory. A restart signs everyone out.

## 1. Key hierarchy per account

```
master password ──Argon2id(salt_a)──▶ KEK_a ──AES-256-GCM wrap──▶ DEK_a (256-bit random, per account)
                                                                      │
                          AES-256-GCM (AAD binds uid and layer) ◀─────┤
                                                                      ▼
                        entry metadata blob, entry content blob (normal entries)
                                                                      │
separate password ──Argon2id(salt_e)──▶ K_entry ──────────────────────▼
                        entry content blob (protected entries; DEK_a cannot open it)
```

- `salt_a` and the Argon2id cost parameters are stored with the account. Each account has its own salt and its own random DEK.
- The login verifier is a separate Argon2id hash of the same password (`password_hash`). It is stored, never the password.
- Different accounts never share a key. Account B's DEK cannot be derived from account A's DEK.

## 2. Account records and roles

| Account | Where stored | Role | Vault key wrapping |
|---|---|---|---|
| Owner | `config/auth.json` (unchanged from v1.x) | `owner` | as today |
| Other accounts | `users` table in the vault database | `user` | same scheme as the owner |

Owner-only operations: create and disable accounts, issue invitations, list accounts. The owner **cannot** decrypt another account's vault. Owner-only routes check the role on the server. Owner-only means "may manage accounts", not "may read entries".

A disabled account's stored wrapped key is kept, but the account cannot log in, and all its sessions are revoked.

## 3. Account creation through invitations

1. The owner creates an invitation for a username and a role. The server generates a 256-bit random token. It stores only SHA-256(token), the expiry (72 hours) and the username and role.
2. The invitee opens the link and chooses their own master password. The server generates their DEK and wraps it under a KEK derived from that password.
3. The invitation is consumed in the same transaction that creates the account, so it is single-use. A second attempt fails.
4. Usernames are unique across the owner and all users, checked inside the transaction.

No shared default password exists, and none is ever generated by the server. The invitation token is not a credential: it lets someone create an account only until it is used or expires.

## 4. Password changes

- The account holder changes their own password with the current password. The new password derives a new KEK, and the **same DEK** is re-wrapped. Entries are not re-encrypted.
- The change is verified before it is committed: the new password must unwrap the same DEK.
- All of that account's sessions are invalidated by incrementing its session epoch.
- **There is no administrative password reset.** The owner cannot recover a user's vault. A forgotten master password means that vault is lost. The owner may disable the account and issue a new invitation, but the old encrypted data stays unreadable.

## 5. Migration from the single-owner vault

Schema v3 to v4 is additive and needs no password:

- Adds `entries.owner_id` (INTEGER, default `0`). Existing rows become the owner's, `0`.
- Creates the `users` and `invitations` tables.
- Sets `packages.owner` from the owner's username to `"0"`, the owner's account ID. Packages stay with the owner, and renaming the owner no longer breaks them.
- Runs in one transaction. It is preceded by an authenticated backup (`pastry backup`, with its manifest and checksums) and followed by verification: row counts match, every package owner is `"0"`, and the SQLite integrity check passes.
- Runs automatically after the owner's password is verified at login, or manually with `pastry migrate`. Nothing is decrypted or re-encrypted, so the migration preserves all entries, custom fields, categories, favourites, separate-password locks, offline packages and timed packages.

## 6. Session isolation

- A session is bound to one account ID and role. It holds only that account's DEK.
- Each account has its own session epoch. Changing a password, or disabling the account, invalidates that account's sessions only.
- Session IDs and CSRF tokens are per session, from `secrets`.

## 7. Entry sharing (implemented)

### 7.1 Keys

```
account password ─Argon2id─▶ KEK ─wrap─▶ account vault key (DEK)
                                              │ seals (AES-256-GCM, AAD binds account and layer)
                                              ├─▶ account X25519 private key
                                              └─▶ per-entry key K_e  (key_blob, AAD: entry uid + key version)

K_e ─AES-256-GCM─▶ entry metadata (name, url, category, favourite, timestamps, lock state)
K_e ─AES-256-GCM─▶ unprotected entry content
separate password ─Argon2id─▶ K_L ─AES-256-GCM─▶ protected entry content   (K_e cannot open it)

for each recipient R:
  eph = fresh X25519 pair
  shared = X25519(eph_private, R_public)
  key = HKDF-SHA256(shared, salt = eph_public || R_public, info = "pastry-share/v1|" + context)
  envelope = eph_public || nonce || AES-256-GCM(key, K_e, aad = context)
  context = version | entry uid | owner id | recipient id | key version
```

- The envelope is bound to one entry, one owner, one recipient and one key generation. Moving it to another entry, recipient or generation fails authentication (tested).
- Every entry has its own random key, so there is no key to hand out that opens anything else.
- The recipient's server-side session unwraps `K_e` with their own private key (itself sealed under their vault key). Nothing about a shared entry is cached beyond the request, except a protected entry's `K_L` after the viewer entered the separate password, and that is dropped as soon as access ends.

### 7.2 Public key binding

Each account's public key is stored with `HMAC-SHA256(binding_key, account id || public key)`. The binding key is derived from `config/release.key` (HKDF), a secret that is not in the database or in backups. A public key whose MAC fails is never used: sharing and rotation fail closed. Someone who can only write to the database cannot redirect wrapped keys. Fingerprints (SHA-256 based, shown in the share dialog) let two people compare keys out of band.

**This does not defend against a malicious or compromised server.** The server holds the binding key, performs the wrapping and decrypts unlocked data, so it can substitute keys. The design makes that one trust boundary, and does not claim otherwise.

### 7.3 Permissions

| Permission | Allows |
|---|---|
| View (always) | Read and copy the credentials. Protected entries still need their separate password. |
| Edit | Change the name, URL and credential content. Not category, favourite, protection, sharing or deletion. |
| Export | Package the entry as `.pastry` (offline or timed). Separate from edit. |

Only the entry's owner can share, change permissions, revoke or inspect access. Every call is authorised on the server. Recipient requests re-read the share row, the key version and the permission flags inside the same transaction as the write.

### 7.4 Revocation and rotation

Revoking one recipient, or everyone, runs in one transaction:

1. delete the share row(s);
2. generate a new entry key `K_e'`; re-seal metadata and unprotected content under it;
3. wrap `K_e'` under the owner's account key and re-issue each remaining recipient's envelope (each remaining public key must verify, or nothing changes);
4. increment the key version.

Server access ends on the next request. An envelope or key from the previous generation no longer opens the entry. **What revocation cannot do:** a recipient who already viewed or copied the credentials keeps what they saw, and a recipient who stored the old `K_e` can still decrypt a copy of the old ciphertext if they obtained one. The server does not hand out ciphertext after revocation. Protected content is under `K_L` and is not re-keyed by revocation; if a recipient also knows the separate password, change it (it is re-sealed under a new key).

### 7.5 Migration to per-entry keys

Schema v5 is additive. Existing entries stay in format 4 and keep working. At each account's next sign-in, that account's entries are converted in one transaction: a fresh `K_e` per entry, metadata and unprotected content re-sealed under it, protected content left byte-identical, IDs and owners unchanged, then every converted entry is read back before commit. Any failure rolls the whole account back, and the entries remain readable in format 4. A backup is taken and verified before the schema migration. No plaintext is written outside the process.

### 7.6 Known limitations specific to sharing

- A recipient must sign in once before they can receive shares (their key pair is created at sign-in).
- Restoring a backup onto a machine with a different `config/release.key` leaves sharing failing closed until `pastry admin rebind-keys` is run after comparing fingerprints.
- The directory endpoint shows active account names to every signed-in account. It lists no keys and no entries.
- The owner of an entry is the only account that can protect, unprotect or delete it. Ownership cannot be transferred.

## 8. Existing secondary-password protection

Unchanged. A protected entry's content is sealed under a key derived from its separate password. The account DEK cannot open it, and no account (including the owner) can bypass that. Changing the account password does not touch protected entries.

## 9. Export and packages in multi-user mode

- Exports include only the logged-in account's entries. Import adds them to that account.
- Packages (offline and timed) carry the owner's account ID. Listing, downloading, revoking and deleting are scoped to that ID. Another account's package ID returns 404.
- Timed-package release keys remain under `config/release.key`, excluded from backups, as before.

## 10. Trust assumptions and unavoidable limitations

- The server operator is trusted. Anyone who can run code in the server process can read any unlocked vault and any password typed into it.
- Passwords are sent to the server over TLS (Tailscale or Caddy). The server sees them briefly, to derive keys.
- Losing a master password loses that vault. This is a deliberate consequence of having no recovery backdoor.
- Account enumeration: login returns the same message for unknown usernames and wrong passwords, and the code always runs an Argon2id verification, so response time does not reveal existence.
- The invitation link is a bearer secret. Anyone who sees it before its owner can register that username, until it is used or expires. Send links only through a channel you trust.
- Backups contain every account's wrapped keys and encrypted data. Their confidentiality depends on each account's master password.

## 11. Weaknesses found in the review and their status

| Finding | Status |
|---|---|
| Packages keyed by username text, so renaming the owner would orphan them | Fixed by the migration to account ID. |
| Session epoch existed only for the owner | Fixed: per-account epochs. |
| No per-account role checks on any route | Fixed: owner-only routes check the role on the server, and a route inventory test enforces authentication and CSRF on every route. |
| Sharing needed per-entry keys, recipient key binding and rotation | Implemented (section 7). |
| Admin password reset would require a recovery path, which would weaken all vaults | Not offered. Documented as a limitation. |
| A server that holds the binding key can substitute public keys | Accepted trust boundary of server-side decryption. Documented. Fingerprints allow out-of-band checks. |
